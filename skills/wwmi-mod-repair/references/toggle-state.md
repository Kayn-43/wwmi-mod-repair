# 搭配状态与持久化

适用症状：菜单/大世界服装不同、每次启动恢复其他搭配、开关失效。它们与贴图漏匹配可能同时存在，应分别验证。

## 先确认替换是否执行

用实际绘制、绑定缓冲区或资源内容确认，不能只读“no draw matched”浮窗。模型完整、服装像原装，也可能是 Mod 自带的 Original 选项。若帧中 Index/Vector/TexCoord/Color/Blend 与 Mod 资源一致，继续检查搭配分支；不要仍按“全部 hash 未命中”修。

列出 Menu、Top、Bottom、形态/Ult 各自保存的变量、键位和循环值。找出用户期望共同控制的状态，保留原作者独立状态。观察游戏中的当前变量与 `d3dx_user.ini` 的相应条目，不把 INI 默认值当成已加载的选择。

## 共享状态与迁移

- 共享一组明确命名的持久变量；大世界按键写入这组状态，绘制前同步到作者已有局部变量。循环值与原选择范围一致。
- 路径自动 namespace 容易随重命名改变，中文/空格路径在不同解析实现中也有差异。采用唯一 ASCII namespace，跨 INI 用 `$\Namespace\variable` 引用；不要据传统解析源码断言当前 DLL 一定有同样缺陷。
- 修改 namespace 前读取旧 namespace 下当前保存的选择，并校验其位于有效循环范围。可将这些值作为新 namespace 的首次默认值；已有新 namespace 保存值照常生效。不在每次 Present 强制重置，也不清空整个 `d3dx_user.ini`。
- 持久变量名称不变不代表身份没变：namespace 与变量名共同确定保存位置。移动目录时重新核对实际路径、namespace 和内容哈希。
- 按键条件若使用不存在的变量，例如未声明的 `$ActiveCharacter`，按真实声明修正；`$object_detected` 是否合适要看当前 Mod，不机械替换全部条件。

保持 hash、匹配范围、绘制和资源路径不变，分别测试：菜单设置→大世界、大世界设置→菜单、完全退出后重启。仅用户确认的范围记为成功。

## 本轮已验证案例

Lucilla 菜单与大世界分别存储服装；帧捕获证明替换已执行。第一版路径式共享引用仍失败；改为 `LucillaOutfitMenu`、迁移8项菜单选择并使用 ASCII 跨 INI 引用后，用户确认菜单/大世界服装一致。Ult 独立系统保留，未宣称所有形态均验证。

Hiyuki 保存搭配问题采用稳定 namespace 与合法按键条件后得到用户确认；其视距错色仍存在，必须另作纹理采集。状态持久化成功不能作为材质修复成功的证据。
